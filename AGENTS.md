# Music Hub

## Zweck & Links

- Läuft produktiv auf https://hub.pleasance.org, https://hub.diespaetzles.lol bleibt parallel erreichbar. Stabilität, Sicherheit und Datenerhalt gehen vor neuen Features.
- Coolify auf VPS 1, Projekt `pleasance-musichub`, getrennte Anwendungen für API, Audio-Worker und Web.
- Das DAW-Plugin `robinchoice/musichub-plugin` spricht dieselbe API. Ausgelieferte Plugin-Versionen müssen nach jedem Update weiter funktionieren, siehe Rückwärtskompatibilität.
- Die CLI in `apps/cli` (Datei `musichub`, README „CLI“) spricht dieselbe API.

## Checks

`bun run check && bun run test && bun --bun run build`, keine neuen Fehler. `test` umfasst die CLI-Tests gegen die API-Routen, `build` baut auch die CLI-Datei `apps/cli/build/musichub`. API- und Browser-Suite bekommen über `packages/db/test.ts` je eine leere Datenbank auf dem Server aus `DATABASE_URL` (Nutzer braucht `CREATEDB`); sie wird auch bei Fehlern und SIGINT/SIGTERM entfernt. Direkte Aufrufe von `bun test` oder `playwright test` umgehen die Isolation. `bun run test` startet auch die Playwright-Tests in `apps/web/tests` (Desktop und Pixel 7): Sie bauen das Web und starten API und Web selbst auf den Ports 31100 und 31101, unter dem Linux-Ephemeral-Bereich (32768–60999) (testen mehrere Worktrees gleichzeitig, per `TEST_API_PORT` und `TEST_WEB_PORT` andere unter 32768 wählen), Chromium einmalig mit `bunx playwright install chromium` in `apps/web`.

## Deploy

- Jeder Push auf `main` geht sofort live: Die CI prüft, baut die Images und deployt über die Coolify-API erst die API, dann den Worker, dann das Web. Auf VPS 1 wird nicht gebaut.
- Prüfen: `gh run watch`. Der Deploy-Job ist erst grün, wenn `https://hub.pleasance.org/api/v1/health` den Commit als `revision` meldet.
- Nach erfolgreichem Deploy fotografiert `screenshots` ausschließlich `/` (Demo mit Beispieldaten) und `/login` ohne Anmeldung in Desktop und Handy, je auf Deutsch und Englisch. Bilder landen als WebP in `docs/screenshots`, der Bot committet mit `[skip ci]` ohne erneuten Deploy. Danach meldet der Job `prototype-deployed` an `robinchoice/pleasance` über `PLEASANCE_DISPATCH_TOKEN`. Vor dem nächsten Push den Bot-Commit holen.
- Destruktive Aktionen (Daten oder Volumes löschen, manuelle Änderungen an der Prod-DB) nur nach ausdrücklicher Freigabe.

## Fallen

- Beim Beenden nimmt die API keine neuen Anfragen an, schließt SSE und wartet auf laufende Anfragen, Upload-Abschlüsse und Mailjobs, bevor sie Postgres schließt. Datei-Uploads gehen direkt nach S3 und überleben einen API-Neustart; der Client bestätigt sie anschließend bei der API. Der Worker bricht ffmpeg ab, wartet auf dessen Ende und gibt erst dann den Audiojob frei. Aufgaben nach der HTTP-Antwort laufen mit `runInBackground` aus `lib/background.ts` und eigener Fehlerbehandlung, damit der Shutdown sie abwartet. Compose lässt beiden 60 Sekunden.
- Secret-Scan: Gitleaks 8.30.1 liest zusätzlich zu `--gitleaks-ignore-path` auch `.gitleaksignore` aus dem Checkout. Der Workflow ersetzt diese Datei deshalb ebenfalls durch die Fassung aus `CONFIG_REF`, bei Fork-PRs aus dem Base-Commit; Merge-Auflösungen und Tags werden mitgescannt.
- Korrelierte Subselects in `sql`-Templates: Bei einem `select` aus nur einer Tabelle rendert Drizzle Spalten ohne Tabellennamen, auch im Template. `exists (select 1 from ${subs} where ${subs.userId} = ${users.id})` wird zu `where "user_id" = "id"`, `"id"` meint dann die Spalte des Subselects, das Ergebnis ist ohne Fehler falsch. Solche Subselects nur in Abfragen mit Join oder mit `alias()`, sonst zwei einfache Abfragen.

- Die Landingpage zeigt die echte Track-Seite im Demo-Modus und ihre Komponenten mit Beispieldaten (`apps/web/src/lib/demo`). Nutzt eine Seite einen neuen API-Endpunkt, braucht `backend.ts` dafür eine Antwort, sonst meldet die Demo „In der Demo nicht verfügbar“.
- Die API ist zustandslos und darf mit mehreren Instanzen laufen. Nichts, was zwischen Anfragen gelten muss, gehört in den Speicher des Prozesses: Rate-Limits stehen in `rate_limits` (`lib/rate-limit.ts`), SSE-Events gehen per Postgres `NOTIFY` an alle Instanzen (`services/sse.ts`, Payload nur IDs, Grenze 8000 Bytes), Migrationen laufen unter einem Advisory-Lock (`migrateDb`).
- Audio verarbeitet nur der Worker (`apps/api/src/worker.ts`, Image `musichub-worker`, ein ffmpeg-Job gleichzeitig). Die API legt Jobs in `audio_jobs` an. Stirbt der Worker, holt er den Job nach Ablauf der Lease (5 Minuten) erneut ab, nach drei Versuchen wird die Version ohne MP3 und Wellenform `ready`. Der Worker leert auch den Papierkorb (alle sechs Stunden). Lokal startet `bun run dev` API und Worker.
- Tempo und Tonart (`versions.bpm`, `key_root`, `key_scale`) erkennt der Worker mit essentia.js (WebAssembly, es gibt keine Essentia-Wheels für arm64) in einem eigenen Prozess (`services/music-analysis.ts`, `nice`), nur wenn kein Audiojob wartet: die neueste spielbare Version ohne `analyzed_at`, so holt er auch alte Versionen nach. Markiert wird beim Nehmen, ein Fehlschlag kommt nicht wieder. Von Hand korrigiert wird im Dialog „Version bearbeiten“ (`PATCH /versions/:id`, Uploader oder Owner); das setzt `analyzed_at` neu, eine laufende Analyse schreibt nur, solange `analyzed_at` noch ihr eigener Zeitstempel ist. Unsicheres bleibt `null` (`parseMusicAnalysis`). Eine Analyse dauert rund 40 Sekunden je Song; wartet ein Audiojob, bricht sie ab (Prüfung alle 2 Sekunden) und die Version kommt später wieder.
- Neue Versionen kündigt die API nicht sofort an, sondern ein Intervall in der API (`lib/notices.ts`, Tabelle `version_notices`, nicht im Worker, der hat kein SMTP und kein VAPID): erst wenn der Uploader 2 Minuten pausiert, spätestens nach 10, als ein Push für alle mit Abo und eine Mail für alle ohne (`users.version_mails`, Abbestellen über `users.mail_token`). So wird ein Schwung aus der Sync-App nicht zu einer Flut. Lokal ohne `SMTP_HOST` stehen die Mails im Log.
- Rückmeldungen (`lib/reviews.ts`, Tabelle `reviews`): „Fertig mit V4“ schließt den Durchgang einer Person, also ihre Kommentare zur Version seit ihrer letzten Rückmeldung, höchstens der letzten `REVIEW_PASS_HOURS`. Wer hochgeladen hat, bekommt dazu einen Push oder ohne Push eine Mail (gleiches Abbestellen wie bei den Versions-Mails). Vergisst jemand „Fertig“, schreibt dasselbe Intervall in der API nach `REVIEW_QUIET_MINUTES` eine Rückmeldung ohne Urteil (`verdict` null) und schickt sie, unter einem Advisory-Lock. Freigeben und Ablehnen über die alten Routen sind auch Rückmeldungen; der Ablehnungsgrund steht in deren `note`.
- Für Agenten lesbar (README, „Für Agenten“): Startseite, Datenschutz und Impressum stehen als Markdown in `publicPages` (`apps/api/src/lib/public-pages.ts`), daraus entstehen `/llms.txt`, `/llms-full.txt` und `<seite>.md`. Ändert sich der Text einer dieser Seiten, im selben Zug dort nachziehen, der Browser-Test vergleicht nur die Überschriften. Hinein kommt nur, was jeder ohne Login sieht, nichts aus Projekten, offenen Tracks oder Profilen.
- Das Repo ist öffentlich, auch seine CI-Logs. `secrets.yml` scannt jeden Push und PR mit gitleaks (README, „Secret-Scan“). Fehlalarme eng abfangen, per Fingerprint in `.gitleaksignore` oder per Pfad und Regel in `.gitleaks.toml`, nie eine Regel ganz abschalten. Ein echter Fund ist schon öffentlich: das Secret sofort rotieren.
- Update-Mails (README, „Update-Mails“, `lib/updates.ts`): Versand in der API wie die Versions-Mails, nicht im Worker, der hat kein SMTP. Agenten schreiben nur Entwürfe als `updates/<slug>.md`, senden darf nur ein Admin aus `ADMIN_EMAILS`. Eine einmal übernommene Datei ändert den Entwurf nicht mehr. Entwürfe haben Deutsch und Englisch (`# de:`/`# en:`), Deutsch liegt in `content` oben, Englisch in `content.en`, ältere Updates haben kein `en`.
- Die WAV-Dateien im Bucket `music-hub` spiegelt VPS 1 nachts vor dem restic-Snapshot und sichert sie mit nach S3 und offsite (`~/dev/kontor/infra.md`, VPS 1). Ein Restore-Test des Spiegels steht noch aus.
- Registrieren geht nur, solange es weniger als `MAX_USERS` Konten gibt (`apps/api/src/lib/users.ts`, wegen des geteilten S3-Speichers). Eingeladene zählen mit, kommen aber immer rein.
- Offene Tracks (`lib/open.ts`, öffentlich unter `/offen`): Ein Remix übernimmt die Spuren mit denselben S3-Keys (`stems.forked`), sie zählen nicht zum Speicher. Dateien löscht nur `deleteUnusedFiles`, das noch genutzte Keys stehen lässt. Öffentlich sind nur Spuren, die vor `open_tracks.opened_at` hochgeladen wurden.
- Profile (`lib/profiles.ts`, öffentlich unter `/@handle`, Route `[handle=handle]`): Ein Chat ist bewusst nicht vorgesehen. Eine Anfrage ist eine einzelne Nachricht. Annehmen legt ein gemeinsames Projekt an oder lädt in eins ein. Ablehnen ist still und sperrt neue Anfragen derselben Person für 30 Tage, Blockieren für immer. Ein Profil zeigt nur offene Tracks, an denen die Person mitgearbeitet hat (offen gestellt, Mix oder eigene Spur hochgeladen).
- Spuren haben Fassungen (`lib/stems.ts`): Die Zeile in `stems` hält immer die aktuelle Datei, frühere liegen in `stem_revisions` und zählen zum Speicher dessen, der sie hochgeladen hat. Wer Speicher zählt oder Dateien löscht, muss `stem_revisions` mitnehmen. Solange ein Track offen ist, lassen sich seine Spuren nicht ersetzen.
- Share-Links (`routes/share.ts`): `share_links.follows` ist `version` (fest an `version_id`), `latest` oder `approved`. Folgende Links zeigen bei jedem Aufruf die neueste spielbare bzw. freigegebene Version des Tracks und pausieren nur mit dem Track, nicht mit ihrer Version; `purgeTrash` hängt sie vorher an eine andere Version, sonst löscht der Cascade sie. Gastkommentare und Gast-„Fertig“ über folgende Links brauchen die gehörte `versionId`, sonst 409. Ein Link kann nie mehr als sein Ersteller: Beim Anlegen werden `allow_comments` und `allow_download` auf dessen Rechte gekappt, beim Aufruf gelten sie nur, solange der Ersteller sie noch hat (`liveTarget`); ohne Kommentare zeigt die Gastseite auch keine Mitglieder-Kommentare.
- Projekt-Links (`project_share_links`, Gastseite `/album/<token>`, Teilen-Dialog der Projektseite): Jede Person im Projekt hat einen eigenen Link fürs ganze Projekt, er folgt `latest` oder `approved`. Gespielt und kommentiert wird über je einen gewöhnlichen Share-Link pro Track (`share_links.project_link_id` und `track_id`), den der erste Aufruf des Projekt-Links anlegt. Die Gastseite nutzt dafür dieselbe Komponente wie `/listen` (`ListenTrack.svelte`). Einstellungen des Projekt-Links schreibt `PATCH` in diese Track-Links mit; Löschen nimmt sie per Cascade mit. Im Teilen-Dialog eines Tracks erscheinen sie nicht.
- Upload-Link (`routes/upload-links.ts`, öffentlich unter `/upload/<token>`): Gäste ohne Konto legen Songs und Spuren an. Beides gehört in der DB dem Ersteller des Links (`created_by_id`) und zählt zu seinem Speicher, den Gast nennt nur `stems.guest_name`. Der Link gilt nur, solange der Ersteller im Projekt hochladen darf, Gäste in seinem Konto zulässt (`users.guest_uploads`) und das Projekt nicht archiviert ist. Was Gäste belegen dürfen, begrenzt `users.guest_storage_limit` (Standard `GUEST_STORAGE_DEFAULT`), gezählt über `guest_name` in `stems` und `stem_revisions`. Notizen der Gäste stehen in `guest_notes` beim Song.
- Track-Status: `sketch` heißt in der Oberfläche „Demo“. `in_progress` („In Arbeit“) stammt von vor den Produktionsphasen und wird nur noch angeboten, solange ein Track ihn hat. Neue Status kennt eine ältere, noch offene Web-Version nicht.
- `test@onboarding.invalid` ist der Test-Account für das Onboarding und zählt nicht gegen `MAX_USERS`. „Als neue Person testen“ im Lagebild setzt ihn zurück (`lib/test-account.ts`, löscht seine Projekte samt Dateien) und kopiert einen Login-Link fürs private Fenster.
- Aufträge (README, „Ablieferung mit Bezahlwand“, `lib/deliveries.ts`, Studio-Routen in `routes/deliveries.ts`, Gast-Routen in `routes/share.ts`): höchstens einer je Projekt-Link (`deliveries.project_link_id` unique). Solange er nicht storniert ist, geben dessen Track-Links nie `downloadUrl` und nie das Original als Stream heraus (ohne MP3 `streamUrl` null und `processing`), und der Projekt-Link meldet `allowDownload` false. Originale gibt es erst nach Bezahlung über `/delivery/download`. Wer neue Wege zu Dateien eines Share-Links baut, prüft `deliveryOfShareLink`. Mitglieder des Projekts behalten in der App ihre Rechte. Einen Projekt-Link mit offenem oder bezahltem Auftrag löscht die API nicht (409 `link_has_delivery`), nur mit storniertem (Cascade). Offene Tracks (`/offen`) nimmt kein Auftrag an (`track_open`), ihr Original ist öffentlich; wird ein Track erst später geöffnet, hält die Bezahlwand ihn nicht.
- Eine Runde gehört zur gehörten Version (`delivery_rounds` unique je Version), ob sie extra ist und ihr Preis (`price_cents`, vom Kunden bestätigt) steht beim Anfordern fest. Sie überlebt das endgültige Löschen ihrer Version (`version_id` null, `version_number` bleibt) und zählt weiter.
- Zahlungen: Geld kann für jede nicht bezahlte Zahlung noch kommen, eine Lightning-Rechnung lässt sich nicht zurückholen. `markPaid` vermerkt sie deshalb aus jedem Status als `paid`; bezahlt ist der Auftrag (`settleIfCovered`), sobald alle Songs freigegeben sind und die bezahlten Beträge die Summe decken (`dueCents` 0, auch bei Summe 0 ohne Zahlung), zu wenig wird angerechnet, zu viel zahlt das Studio zurück. Neue Zahlungen und Storno lassen offene Zahlungen verfallen, Runden und PATCH nur `pending`, eine angekündigte Überweisung bleibt offen. Lightning-Rechnungen fragt die API bis `LIGHTNING_GRACE_MS` nach Ablauf bei der Wallet ab, auch ersetzte (`checkLightningPayments`: Poll, vor neuer Zahlung, API-Intervall); danach markiert das Studio von Hand.
- Geld fließt nie über uns: Lightning über die eigene Wallet des Studios per NWC (`lib/payments/nwc.ts`), nur Verbindungen ohne Zahlrechte (`checkReceiveOnly`, Allowlist `RECEIVE_ONLY_METHODS`), Überweisung an seine IBAN mit GiroCode. Den Zahlungsstatus fragt immer die API bei der Wallet ab, nie der Browser. Relays wählt der Nutzer: die API wählt nur öffentliche `wss://`-Hosts an (`relayProblem`, nach DNS nochmals), nie Loopback, private, Link-local oder CGNAT. Die NWC-Verbindung liegt mit `PAYMENT_SECRETS_KEY` verschlüsselt in `payment_accounts`, nie in Antworten oder Logs; ohne den Key gibt es kein Lightning, ein neuer Key macht gespeicherte Verbindungen unlesbar.
- Aufträge anlegen nur mit `users.plan = 'solo'` (in der Oberfläche „Studio“, bis `plan_until` oder ohne Ende) oder als Admin aus `ADMIN_EMAILS`. Den Tarif setzt ein Admin im Lagebild oder eine Zahlung.
- Tarife (README, „Tarife“, `lib/billing.ts`): Eine Zahlung schiebt nur `plan_until`, ein Tarif hebt das Speicherlimit nur an, Ende löscht nie etwas. Grenzen und Preise nur in `constants/plans.ts` ändern, die SQL-Fassung in `storage.ts` (`limitSql`) zieht mit. Stripe und BTCPay sind aus, solange ihre Variablen fehlen. AGB, Widerrufsbelehrung und der Datenschutz-Abschnitt zu Zahlungen stehen nur in `packages/shared/src/terms.ts` und sind nur öffentlich, solange ein Zahlungsweg gesetzt ist (`plansForSale`, `GET /billing/offer`); `/agb` steht deshalb auch in `isPublic` des Root-Layouts. Kündigen und Widerrufen gibt es nur über `/billing/cancel` und `/billing/withdraw`, die Erstattung macht ein Admin von Hand.
- Speicher und Backup: Den Bucket spiegelt VPS 1 jede Nacht auf das Volume `vps1-data` (60 GB, darauf liegt auch Docker). Wächst der Bucket über den freien Platz darauf, fällt das Backup aus und im schlimmsten Fall jeder Dienst auf VPS 1. Tarife mit 100 bzw. 500 GB erst verkaufen (Stripe- und BTCPay-Variablen setzen), wenn das Bucket-Backup ohne den Volume-Spiegel läuft, und bis dahin Pro und Studio auch von Hand nur vergeben, wenn der Bucket Platz hat. Verwalten darf jeder Owner des Projekts, das Geld geht an das Konto von `deliveries.created_by_id`.

## Konventionen

- TypeScript prüft `strict` und `exactOptionalPropertyTypes`; Biome verbietet explizites und sich implizit entwickelndes `any`. Unbekannte Eingaben sind `unknown` und werden mit zod geprüft, Bibliotheksantworten und gespeicherte Werte per `safeParse`. Die Prozesseinstiege importieren `apps/api/src/env.ts` zuerst; neue Env-Variablen mit Pflichtwert oder Format dort ergänzen. Optionale Felder für Bibliothekstypen mit `.exactOptional()`, Typfehler an der Ursache beheben.

- Zugriff in der API: Wer ein Projekt, einen Track oder eine Version anfassen darf, holt `lib/access.ts` (`membershipOf`, `trackAccess`, `versionAccess`) zusammen mit dem Objekt, inklusive Papierkorb-Regel; in einem archivierten Projekt ruhen dort die Rechte zum Hochladen, Kommentieren und Freigeben, die Rolle bleibt. Keine eigene `projectMembers`-Abfrage in Routen. Die Antwort auf eine fehlende Mitgliedschaft bleibt bei der Route: Lesen 404, Schreiben 403. Originale (Version, Spur, Fassung, ZIP, `audio?quality=original`) gibt es nur mit `mayDownload` aus denselben Rollen (`track.download` in `permissions.ts`, viewer und label haben es nicht), Anhören bleibt für jedes Mitglied. Eine Version umbenennen darf ihr Uploader oder der Owner.
- Speicher: Jede Zählung baut auf der Liste `uploadedFiles` in `lib/storage.ts` (`storageOf`, `guestStorageOf`, `storageSummary` für die Übersicht, `storageByUser` für den Admin). `stems.test.ts` prüft, dass sie übereinstimmen. Beim Löschen eines Tracks liefert `fileKeysOfTracks` in `lib/trash.ts` alle Dateien darunter, Cover eingeschlossen.
- Web: Rechte und Status-Gruppen kommen aus `lib/utils/track.ts` (`capabilities` mit `canDownload`, `isProcessing`, `isDecided`), keine Rollen- oder Statusvergleiche von Hand. Sicherheits-Header setzt `hooks.server.ts` wie im starter, die CSP steht in `svelte.config.js`: Neue externe Quellen (Bucket-Host, Dienste) gehören dort hinein, sonst blockt der Browser sie still. Die Seitenleiste zeigt Projekte und Tracks des Overview-Stores (`/overview`), ohne eigene Kopie; nach Änderungen an Projekten oder Tracks `reloadSidebar` aus dem Context des App-Layouts aufrufen, es lädt den Store neu.
- Ein Push ist nur ein Signal: Ereignistyp und Objekt-ID oder Cursor, keine Inhalte und keine personenbezogenen Daten, wegen des Datenschutzes (Grundsätze 1 und 2). Die App holt die Daten über einen Endpunkt hinter `requireAuth` ab ihrem letzten Cursor (`since`) und fragt ihn auch beim Öffnen und regelmäßig ab, so schaden verlorene oder doppelte Pushes nicht. SSE und Web-Push folgen dem. Web-Push enthält nur `type: notification` und eine ID; Details stehen sieben Tage in `push_notifications`, das API-Intervall löscht ältere Einträge. Der Service Worker ruft sie mit Session-Cookie über `/api/v1/push/notifications/:id` ab, mit erneuter Empfänger- und Berechtigungsprüfung. Fehler bleiben neutral. Beim Öffnen und jede Minute im Vordergrund holt er verpasste Einträge über `since` nach; der Cursor ist kontogebunden, Benachrichtigungs-Tags sind stabile IDs, bereits angezeigte IDs merkt er sich sieben Tage ohne Inhalte. Ein geschlossener Browser kann ohne zugestelltes Push-Signal erst beim nächsten Öffnen nachholen.

- CLI (README, „CLI“): Jedes Kern-Feature bekommt im selben Zug einen Befehl in `apps/cli/src/commands` nach dem Beispiel `projects.ts`, mit Text und `--json` und einem Test in `cli.test.ts`. Die CLI spricht nur mit der HTTP-API, nie mit der Datenbank, so gelten Rechte, Rate-Limits und `MAX_USERS`. Agenten melden sie nur mit admin@pleasance.org an (`login-link musichub | apps/cli/build/musichub login --link -`), nie mit Kundenkonten.

Das Widget und die Einführung samt neuem HMAC-Key in `server_secrets` brauchen eine abgestimmte Freigabe.

- PostHog bleibt nach Robins Entscheidung vom 17.10.2026 deaktiviert.

Ihre Texte stehen nur auf Englisch in `apps/cli/src/texts.ts` statt in shared, `--lang` entfällt; sie schickt `Accept-Language: en` (Robin, 27.10.2026: die Welt der Kommandozeile ist Englisch).
- Sprachen wie im starter (Deutsch und Englisch, Umschalter in der Fußzeile, Cookie `locale`, sonst `Accept-Language`), aber Texte pro Bereich: Web in `apps/web/src/lib/i18n/<bereich>.ts` (`t().<bereich>.…`), API in `apps/api/src/lib/messages.ts`, Labels in shared als `{ de, en }` (`ROLE_LABELS[locale]` usw.). Die API antwortet in der Sprache des Cookies, sonst `Accept-Language`; das Plugin schickt keins und bekommt Deutsch, die CLI Englisch. Mails und Pushes an andere gehen in deren Sprache (`users.locale`, gesetzt beim Login und von `/auth/me` des Webs). Deutsch bleiben nur Admin-Seiten und Admin-Mails (nur `ADMIN_EMAILS`). Jeder neue Text kommt auf Deutsch und Englisch.
- Update-Mails verschickt die API in einer Schleife (`deliverUpdates`), nicht ein eigener Worker wie im starter: Der Audio-Worker hat kein SMTP. Takt und Sperre liegen in Postgres, mehrere API-Instanzen teilen sich den Versand.
- Die Health-Route der API heißt `/api/v1/health` statt `/api/health`, umbenennen verbietet die Rückwärtskompatibilität. Der Deploy-Job prüft dort die `revision`.
- Der Papierkorb-Purge läuft im Worker per `setInterval` statt über eine Zeitplan-Tabelle: Er ist idempotent, ein doppelter Lauf findet nichts mehr, ein verpasster holt beim nächsten nach.
- Link-Vorschau nach dem starter (AGENTS.md, „Link-Vorschau“): je Sprache ein Bild `static/og-image-<de|en>.png`. Nach Änderung von Claim, `APP_BAND` oder Kachel (`static/favicon.svg`) mit `bun run og-image` in `apps/web` neu rendern und committen.

## Rückwärtskompatibilität

Gilt für Daten, API und URLs. Interner Code darf weiterhin direkt umgebaut werden.

- Jedes Update muss mit den bestehenden Daten und mit bereits ausgelieferten Clients funktionieren. Web und API deployen getrennt, und der Service Worker hält alte Web-Versionen eine Weile am Leben.
- Migrationen nur additiv (expand/contract): kein `DROP`, kein Umbenennen, keine engeren Typen, keine neue `NOT NULL`-Spalte ohne Default. Alte Spalten erst entfernen, wenn kein deployter Code sie mehr nutzt, und nur nach Rückfrage.
- Migrationen laufen beim API-Start automatisch. Sie dürfen bestehende Daten nie löschen oder verlustbehaftet umschreiben.
- API: Endpunkte und Felder nur hinzufügen, nichts entfernen oder umbenennen. Neue Request-Felder sind optional und haben einen Default.
- Hochgeladene Dateien (S3): Bestehende Keys bleiben gültig. Ein Update löscht oder verschiebt keine Objekte.
- Bestehende URLs (Share-Links, Projekt- und Track-Seiten) bleiben erreichbar.
- Secrets, an denen Daten hängen, bleiben unverändert: `MAGIC_LINK_SECRET` (Sessions), VAPID-Keys (Push-Abos), S3-Bucket.
